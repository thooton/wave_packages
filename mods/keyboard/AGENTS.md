# Keyboard Improved

Read [the shared constraints](../AGENTS.md) for building and testing.

**The stock APK is not in this repository.** `XT9IME.apk` is Nuance's, so the module carries
only the built dex (`apps/XT9IME/apktool` smali with the hooks, plus `java/`) and a small
splicer (`tools/splice`). `module/customize.sh` runs it with `app_process` when Magisk
installs the module: it checks the phone's stock APK against `module/stock.sha256` (11.20.00;
through Magisk's mirror, so an update doesn't read the old overlay), copies every stock entry
as its raw bytes (META-INF too: Android 8.1 checks a system APK's v1 signature against the
manifest only, see `../tools/splice_apk.py`), stores the dex uncompressed where the stock dex
was, drops the v2 signature block, and reads the result back to verify it. Nothing depends on
the phone's zlib. To build the whole APK on the host as well, put the stock APK at
`mods/firmware/system/app/XT9IME/XT9IME.apk` (ignored by git) or set `XT9IME_STOCK`;
`tools/build.sh` then splices it, runs `verify_splice.py`, zipalign and linkcheck on it.

`tools/build.sh` builds the dex and the splicer (always; that's all CI can do), `tools/test.sh`
tests the splicer on a synthetic APK and checks that the smali tree is exactly what
`tools/apply_hooks.py` makes, `tools/package.sh` makes `out/keyboard-improved-<version>.zip`,
`tools/deploy.sh` installs that zip with `magisk --install-module` (as Wave does) and reboots.
CI builds mods with `tools/build.sh` and `tools/package.sh` directly: `mods/tools` and
`mods/firmware` are in every mod's release scope, so changing them would require releasing
every mod.

## Code

All logic is Java in `apps/XT9IME/java/com/nuance/flext9_OEM/input/Wave*.java`; the smali
changes are only the hooks listed in `tools/apply_hooks.py` (run it on a fresh
`apktool d -r` of the stock APK to recreate the tree). `WaveAlpha` is generated by
`tools/gen_wavealpha.py` from jadx's `NativeAlphaInput.java` (`tools/decompile.sh XT9IME`):
every engine call goes through `WaveSpec.enter/exit` or one of its answering methods.

- `WaveSpec`: the engine look-ahead (see its class comment). Its invariant: the engine's
  state and every answer the stock code gets are exactly what stock calls would have given.
  Calls are either answered from a record (processKey, wordSelected, clearAllKeys, the build,
  pure reads) or made for real after `settle()` (which applies recorded states and replays
  answered calls). A call that isn't known to be pure invalidates the records.
- `WaveMem`: snapshots of the engine library's state blocks (layout of the 11.20.00 library,
  checked at start; on any mismatch the look-ahead stays off). After each look-ahead key the
  state is copied out and the engine put back whole; the copy is compared with its base on
  the `WaveCmp` thread while the look-ahead goes on, and the record is kept once that is
  done (`drain` before a base changes and before a look-ahead ends).
- `WaveEarly`: letters on key down (stock types them on release).
- `WaveFrame`: draws as soon as the suggestions are set; skips drawing words outside the bar;
  remembers candidate widths across keys (`measure`, keyed by text and every width-relevant
  Paint setting; a miss calls `Paint.measureText`, and with debug on every hit is checked).
  The look-ahead's candidates are measured ahead on the `WaveMeasure` thread (`prepare`) with
  copies of the Paints seen.
- `WaveConnection`, `WaveStatus`, `WaveDisplay`, the `checkEULAInfo` reorder: no synchronous
  IPC while a key is handled, with the same answers.
- `WaveBoost`: CPU minimum frequency at the top while typing (BoostFramework perf lock), and
  the main thread and RenderThread(s) at audio priority from a key event until 120 ms after
  the last one (threads started meanwhile get the main thread's priority back). The
  look-ahead thread runs at nice 9 and at display priority while a key waits for it.

## Debugging and parity

`setprop debug.wave.keyboard 1` (then restart the keyboard) logs to tag `WaveKeyboard`:
every engine call and whether it changed the engine (a pure call that does is reported),
look-ahead misses, and the suggestion list after each update (`cands sel=N [...]`).
`setprop debug.wave.keyboard.noraise 1` turns the priority raise off (read per key, for A/B
runs). `setprop debug.wave.keyboard.off 1` turns the look-ahead off, which gives the stock engine
call sequence: typing the same keys with it on and off, from the same databases, must give
identical `cands` lines and identical `files/*.bin`. Trace sections (`wave.*`, `xt9.*`) show
in atrace with `-a com.nuance.flext9_OEM.input`.

Don't drive the phone UI, deploy or reboot while another agent is using the phone.
